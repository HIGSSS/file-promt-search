# Backend — Intelligent File Search

FastAPI-сервер: индексация файлов, семантический поиск, гибридный скоринг.

## Требования

- Python 3.10+ (рекомендуется 3.10–3.12; 3.14 не поддерживается пакетами ML)
- 4+ ГБ свободной RAM (модели SigLIP + SBERT + EasyOCR)
- ~3 ГБ свободного диска для весов моделей (скачиваются при первом запуске)
- GPU (опционально) — torch автоматически использует CUDA при наличии

## Быстрый старт

```powershell
# Windows — создать venv и установить зависимости
cd backend
py -3.10 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

# Запустить сервер
.venv\Scripts\python.exe -m uvicorn main:app --host 0.0.0.0 --port 8000
```

```bash
# Linux / macOS
cd backend
python3.10 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --host 0.0.0.0 --port 8000
```

Сервер поднимается на `http://0.0.0.0:8000`.
При первом запуске модели скачиваются автоматически (~10–20 минут).

## Проверка через curl

```bash
# Запуск индексации
curl -X POST http://localhost:8000/index \
    -H "Content-Type: application/json" \
    -d '{"path": "/абс/путь/к/папке"}'

# Статус индексации
curl http://localhost:8000/status

# Поиск
curl -X POST http://localhost:8000/search \
    -H "Content-Type: application/json" \
    -d '{"query": "кот у окна", "file_type": "all", "top_k": 10}'

# Проверка работоспособности
curl http://localhost:8000/health
```

```
│   ├── image_processor.py   # SigLIP (визуальный вектор) + EasyOCR (текст)
│   ├── video_processor.py   # 5 кадров → усреднение SigLIP (CPU/CUDA)
```


## Изменения и улучшения

### OCR: EasyOCR вместо PaddleOCR

PaddleOCR требовал PaddlePaddle — отдельный тяжёлый ML-фреймворк,
который конфликтовал с PyTorch через общий oneDNN-контекст (ошибка
при одновременной инициализации). EasyOCR работает поверх того же
PyTorch, что SigLIP и SBERT — конфликта нет, установка проще.

### OCR встроенных изображений в PDF

Раньше OCR применялся только к страницам без текстового слоя (сканам).
Теперь для текстовых страниц дополнительно распознаются вставленные
в них фото и скриншоты: текст на них попадает в индекс наравне
с обычным текстом документа.

Ограничения для производительности:
- не более 20 встроенных изображений на документ (`EMBEDDED_IMAGES_LIMIT`)
- иконки и декоративная графика < 80 px пропускаются (`EMBEDDED_IMAGE_MIN_SIDE`)

### Исправлена индексация видео

При forward-проходе SigLIP кадры не переносились на устройство модели
(CPU/CUDA). Из-за этого видеофайлы молча выпадали из результатов
поиска — исключение перехватывалось выше, и `image_vec` не записывался.
Добавлен явный `inputs = {k: v.to(DEVICE) for k, v in inputs.items()}`.

### Уточнены категории фильтрации поиска

| `file_type`  | Охватываемые форматы                                        |
|-------------|--------------------------------------------------------------|
| `images`    | Изображения (`jpg`, `png`, `gif`, …)                         |
| `videos`    | Видеофайлы (`mp4`, `avi`, `mov`, …)                          |
| `documents` | Только `pdf` и `docx`                                        |
| `other`     | `txt`, `csv`, `xlsx`, `pptx`, `odt`, `rtf`, `md`, `log`, … |
| `all`       | Все форматы                                                  |

### Поддержка GPU

`torch` настроен на автоматическое определение CUDA. На машинах с GPU
SigLIP и SBERT автоматически переносятся на него — ускорение индексации
в несколько раз. На CPU-машинах поведение не изменилось.

### Ленивая загрузка переводчика

Модель Helsinki-NLP/opus-mt-ru-en (ru→en, для медиа-поиска с русскими
запросами) больше не загружается при старте сервера — только при первом
реальном использовании. Это сокращает время холодного старта.

### Архитектурные решения (из ТЗ)

- **Два FAISS-индекса** (media 768D + text 384D) — векторы разной
  размерности нельзя смешать в одном `IndexFlatIP`.
- **Агрегация по `filepath` в searcher'е** — FAISS возвращает два
  вектора одного файла как отдельные hit'ы; агрегация необходима для
  гибридной формулы `0.6·image + 0.4·text`.
- **Атомарная запись индексов** через `.tmp` + `os.replace` — защита
  от гонки между фоновой индексацией и одновременным `/search`.
- **Thread-safe `index_state`** с `threading.Lock` + `try_start()` —
  защита от повторного запуска параллельной индексации.
- **Порог «осмысленного текста»** для PDF — определяется числом слов
  длиннее 2 символов, а не только длиной строки: колонтитул
  «стр. 5 из 42» больше не считается текстовой страницей.
- **PyMuPDF вместо PyPDF2 + pdf2image** — одна библиотека, не требует
  системного Poppler.

## Известные ограничения

- Сервер работает на ПК — ML-модели не помещаются в RAM мобильного устройства
- Индексация на CPU: ~1–5 сек на файл
- `.doc` (старый бинарный Word) не поддерживается — только `.docx`
- Зашифрованные PDF пропускаются без ошибки
- Индекс типа Flat: точный, но линейный по числу векторов;
  для 100k+ файлов стоит перейти на HNSW или IVF
